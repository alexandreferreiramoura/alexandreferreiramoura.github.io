UNIT 3 — Controlando Entregas (Exercício 5 — 6 tasks internas)

Contexto

Customizing pesado: criação de tipo de entrega e categoria de item próprios, controlando picking relevance, minimum quantity, documento precedente, e validação de ponta a ponta.

Conceitos-chave

Nível DELIVERY TYPE controla:
  - Faixa de numeração (numeração interna)
  - Tipo de documento precedente exigido

Nível DELIVERY ITEM CATEGORY controla:
  - Picking relevance
  - Checagem de quantidade mínima

Sequência executada

1. ZA## (Trade Fair88-Order) → campo Delivery type alterado de LF para ZL88
2. Copy control: Specify Copy Control for Deliveries
   → ZL88 aceita como origem tanto ZA88 quanto OR (Standard Order)
3. Item Category ZA88 criada via "Copy As" a partir de TAN
   → Dependent entries confirmadas (Yes)
4. Assign Item Categories: ItCG NORM + Sales Doc Type ZA88 → DfItC alterado de TAN para ZA88
5. Delivery Item Category ZA88 → Overdelivery = B (Cancel action, display error message)
6. Teste de ponta a ponta:
   Sales Order 413 (ZA88, C610-A88, qtd 12) → item category ZA88 confirmada
   → Deliver → Delivery type ZL88 confirmado
   → Alterar qtd para 15 → erro "Delivery quantity is greater than target quantity 12 PC"
   → Reverter para 12
   → Adicionar item P610-288, qtd 5 → categoria DLN (determinação automática)
   → Save → Delivery 20000006 (faixa 20000000-24999999 confirmada)

🔧 Pegadinhas

  • É essencial garantir estar na tela "Details" de ZA88 no campo SaTy antes de alterar o Delivery Type — fácil de editar o registro errado se a navegação não for cuidadosa.

✅ Diagnóstico AMS — Unit 3

  • Este exercício mapeia exatamente o encadeamento que se investiga em um chamado "a entrega saiu com tipo errado" ou "o pedido não permite entrega parcial maior que a solicitada": Sales Doc Type → Delivery Type (VOV8) → Copy Control (delivery↔sales doc) → Item Category Determination → Item Category Overdelivery flag.

Exercício 12 — Criar Warehouse Task e Confirmar

🔴 Bloqueio investigado a fundo (objeto 30000):

Tentativa inicial de criar a Warehouse Task pelo botão "Process Codes" na grid de itens do Outbound Delivery Order (dentro da tela "Maintain Outb. Deliv. Order") levou a um Process Code único disponível — "0003 Warehouse Difference, No Adjustment" — que, apesar da mensagem "Activity was carried out successfully", não criou nenhuma Warehouse Task real (consulta genérica sem filtro no Monitor confirmou zero tarefas no sistema).

Caminho correto identificado (via roteiro oficial + investigação):

Maintain Outb. Deliv. Order → selecionar item → menu superior
  "Outbound Delivery Order" → Follow-On Functions → Warehouse Task
  → Abre tela dedicada "Create Warehouse Task - Stock Removal"
  → Marcar linha da Warehouse Request → botão "Create + Save"

Resultado: Warehouse Task 10400 criada (Process Type Y214, Stock Removal, Activity PICK, 10 PC de P610-588).

Confirmação:

Warehouse Management Monitor → selecionar WT 10400
  → More Methods → Confirm WT in Background
  → Log: "Warehouse task 10400 is to be confirmed" / "was confirmed"
  → Gera automaticamente task complementar: 10000900 (2 itens, também confirmada)

Repetição no objeto novo (419/20000010), aplicando direto o caminho correto: Warehouse Task 20365 criada e confirmada sem incidentes, usando o caminho Follow-On Functions desde o início (sem passar pelo Process Code de ajuste).

Exercício 13 — Postar Goods Issue

🔴 Bloqueio prolongado — investigação de causa raiz:

Ao tentar "Goods Issue" na tela do Outbound Delivery Order (tanto no objeto 30000 quanto no novo 419/20000010), o sistema retornou repetidamente o erro:

Delivery 30000: No quantity available for goods movement
(Message Class /SCWM/GOODS_MOVEMENT, message 025)

Passos de investigação executados: 1. Confirmado que a WT de picking estava 100% Confirmed (via TANUM Warehouse Task, Act. D. Qty = 10/10, DiffQty = 0) — descartada falha na tarefa em si. 2. Confirmado que a task complementar automática (10000900) também estava Confirmed — descartada tarefa pendente. 3. Consultado estoque físico via Available Stock (Stock and Bin → Storage Bin → Available Stock): confirmou baixa real de 10 PC (100 → 90 PC, batendo exatamente com a WT confirmada) — descartado problema de estoque físico ausente. 4. Consultada a coluna de Quantity no item da entrega (aba Items): estava em 0, apesar da picagem física confirmada — apontando dessincronia entre EWM (armazém) e o campo de quantidade do documento LE. 5. Tentativa de forçar sincronização via menu "Outbound Delivery Order" → "Set to Ready for Shipping": retornou "Status could not be set for 1 warehouse requests". 6. Consultada a aba Status do item: revelou que DPI (Picking) = Completed, DWA (Warehouse Activity) = Completed, DGI (Goods Issue) = Completed, DCO (Completion) = Completed — ou seja, o processamento em background já havia sido concluído com sucesso, apesar da mensagem de erro na tela. 7. Confirmação final via Stock – Single Material: identificado que a tela de consulta estava usando uma data de seleção desatualizada (não cobrindo o registro mais recente) — ao ajustar a data no cabeçalho da consulta, o estoque real apareceu corretamente em 80 PC (baixa acumulada dos dois ciclos de GI, confirmando que ambos os Goods Issue — do objeto 30000 e do objeto 419/20000010 — haviam sido postados com sucesso).

Resultado: Goods Issue confirmado como postado com sucesso em ambos os objetos, apesar da mensagem de erro enganosa na tela de execução.

✅ Diagnóstico AMS — Unit 5 (o mais valioso da prática)

  1. "Process Codes" ≠ "Follow-On Functions → Warehouse Task". O botão Process Codes na grid de itens do Outbound Delivery Order serve para ajustes/diferenças de estoque, não para criação da tarefa de separação padrão. Em chamados reais tipo "não consigo criar a tarefa de picking no EWM", o primeiro ponto a checar é se a navegação caiu na função de Follow-On correta ("Warehouse Task" via menu do documento) e não em uma tela de ajuste genérico — usar o caminho errado pode gerar uma mensagem de "sucesso" que não corresponde à ação real desejada.

  2. Confirmação de WT em Stock Removal pode gerar uma segunda tarefa automática (movimento até área de staging/expedição) — comportamento padrão do fluxo de picking em dois passos do EWM. Já em Putaway (entrada), a task complementar pode vir já confirmada automaticamente junto com a principal, sem necessidade de ação manual adicional.

  3. Telas de monitor/consulta do EWM com filtro de data podem exibir dados desatualizados mesmo quando o processamento em background já foi concluído com sucesso — isso pode simular um erro de sincronização quando, na realidade, é apenas um problema de filtro de período na tela de consulta. Antes de assumir falha real de integração, sempre checar: (a) status da Warehouse Task via consulta direta (TANUM), (b) estoque físico via Available Stock/Physical Stock, e (c) a aba Status do documento de entrega (campos DPI, DWA, DGI, DCO) — esses três pontos, juntos, dão o diagnóstico definitivo, independente do que uma tela específica de execução esteja mostrando no momento.

  4. Mensagens "No changes made, no save required" não são necessariamente erro — podem indicar que a ação anterior já havia persistido os dados com sucesso, e a tentativa seguinte de salvar não encontrou nada pendente.

🎯 Resumo executivo — Aprendizados-chave

  1. Estrutura de determinação em cascata do SD: Sales Doc Type → Delivery Type (VOV8) → Copy Control → Item Category Determination → Item Category (regras de overdelivery, picking relevance) — é a cadeia a seguir sempre que um chamado envolver "tipo de documento errado" ou "regra de negócio não aplicada" na entrega.
  2. Determinação automática de Shipping Point e Rota segue uma cadeia de chaves específica: Shipping Condition + Loading Group + Plant → Shipping Point; depois Shipping Point + Customer + Shipping Condition + Transportation Group (+ Weight Group na entrega) → Rota. Um dado de teste errado (ex: Loading Group do material) é a causa mais comum de "a determinação não funcionou".
  3. Cada entrega LE tem um espelho no EWM com numeração independente (Outbound Delivery Order / Inbound Delivery EWM) — essencial para navegar entre os dois mundos ao investigar um chamado.
  4. A criação de Warehouse Task tem caminho específico (Follow-On Functions, não Process Codes) — usar o caminho errado não gera erro explícito, mas também não produz o resultado esperado.
  5. Erros de tela nem sempre significam falha real de processamento — no EWM, sempre vale conferir o status consolidado do documento (aba Status) e o estoque físico antes de assumir que uma ação falhou definitivamente.
  6. GR Preparation - External Procurement permite criar a Inbound Delivery direto no EWM (sem depender do fluxo padrão via LE), usando ASN como referência — rota alternativa útil quando o recebimento é gerenciado integralmente pelo warehouse.
