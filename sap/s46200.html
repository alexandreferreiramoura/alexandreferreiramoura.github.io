UNIT 1 — Using the Condition Technique in Pricing (Exercícios 1–6)

Contexto

Introdução prática à cadeia completa: Pricing Procedure → Condition Type → Access Sequence → Condition Table → Condition Record.

Sequência executada

Ex.1: Pedido sem PR00 → erro "Mandatory condition PR00 is missing"
      → Criar PR00 genérico (Material, 280 EUR) → pedido 420 confirma
      → Criar PR00 escala (Customer/Material: 250/240/230) + K007 escala (2/3/5%)
      → Pedido 421 confirma PR00=240 (escala "From 10") + K007=3%
Ex.2: Verificar Customizing do K007 → Calculation Type A (%), Scale base type B (Value scale)
Ex.3: Definições conceituais — Pricing Procedure / Access Sequence / Condition Type
Ex.4: Adicionar RC00 manual (-10 EUR/PC) → Cond.Control = C (Changed manually) confirmado
Ex.5: HB00/RB00 no cabeçalho, 2 itens → RB00 replicado integral, HB00 rateado proporcional
Ex.6: RC00 manual (-100 EUR/PC) → ciclo completo Order→Delivery→Invoice
      → Pricing Type G (padrão LF→F2) preserva RC00 na fatura
      → Pricing Type B (forçado manualmente) descarta RC00 (só redetermina automáticos)

🔧 Pegadinhas

  • RC00 "Amount" é sempre por unidade (EUR/PC), não valor total — digitar "10" pensando em desconto total de 100 EUR (10×10) é erro clássico de 10x.
  • Group Condition (HB00) é rateada proporcionalmente; condição simples (RB00) é replicada integralmente em cada item.
  • Pricing Type no Copying Control (delivery→billing) determina se condições manuais sobrevivem: G (padrão F2) preserva tudo; C (F1) redetermina automáticos mas preserva manuais; B (forçado) descarta manuais.
  • Cond.Control = C é o campo que denuncia alteração manual pós-determinação automática; Condit.Origin = A mostra que a condição nasceu automática antes de ser editada.

✅ Diagnóstico AMS

  • "Mandatory condition PR00 is missing" → material sem registro de preço cadastrado (VK11/Manage Prices) para a combinação Sales Org/Canal.
  • "Desconto negociado sumiu na nota fiscal" → alguém rodou reprocessamento de preço (Pricing Type B / New Pricing Document) na fatura, que descarta condições manuais.
  • "Desconto de cabeçalho não bateu o esperado nos itens" → verificar se a condição é Group Condition (rateio) ou não (replicação integral).

UNIT 2 — Configuring Pricing (Exercícios 7–9)

Contexto

Navegação profunda no Customizing: sequência de acesso do PR00 (PR02), determinação do procedimento de precificação, e construção de um Pricing Model completo do zero — o exercício mais crítico e mais longo da trilha inteira.

Sequência executada

Ex.7: PR00 → Access Sequence PR02 → 3 acessos (305/306/304)
      Acesso 30 (304) tem Requirement 3 (só roda se moeda estrangeira) — otimização de performance
Ex.8: Customer Pricing Procedure do cliente = 1 (Standard)
      Document Pricing Procedure do tipo OR = A
      Determinação: 1010/10/A/1 → RVAA01
Ex.9: Construção completa "do zero" de um pricing model:
      Condition Table 788 → Access Sequence ZA88 → Condition Type ZF88
      → Pricing Procedure Z88PRC → Customer Pricing Procedure C9
      → Determinação 1010/10/00/A/C9 → Z88PRC
      → Cliente C620-A88 atualizado para CuPP=C9
      → Registro VK11 ZF88 = 10 EUR/kg
      → Pedido 433 confirma ZF88 funcionando (12,50 EUR = 10×1,25kg)

🔧 Pegadinhas — INSTABILIDADE GRAVE DO SISTEMA (a mais importante da trilha)

Sintoma: ao tentar atribuir os campos (VKORG/INCO1/LLAND) dentro da Access Sequence ZA88 (Dialog Structure: Access Sequences → Accesses → Fields), o sistema simplesmente não salvava — a tela de Fields vinha sempre vazia, mesmo após múltiplas tentativas, novo login, tabela nova (988), e sequência nova (ZA90).

Causa raiz real (descoberta após ~2h de diagnóstico): o duplo clique na pasta "Fields" da árvore (Dialog Structure) não funciona de forma confiável nessa transação do SAP GUI clássico quando é preciso que o sistema saiba qual linha específica de "Access" (10) usar como referência. A navegação correta é: selecionar a linha (clique único) + Enter, não duplo clique na pasta.

Trilha de diagnóstico percorrida (útil para reconhecer o padrão em outros contextos): 1. Runtime Error ASSIGN_TYPE_CONFLICT (dump ABAP) ao tentar entrar em Fields após gerar a tabela 788 → suspeita de buffer corrompido 2. Recriação da tabela com número novo (988, com campo extra VTWEG para evitar duplicidade de chave) → mesmo problema 3. Recriação da Access Sequence com nome novo (ZA90) → mesmo problema, inclusive em sequências padrão já existentes do sistema (não só as customizadas) 4. Verificação de locks (SM12) → 0 locks 5. Verificação de update requests pendentes (SM13) → 0 registros 6. Conclusão: não era lock, não era update pendente, não era objeto corrompido — era método de navegação errado

Nota de precificação: o roteiro do exercício avisa que criar uma tabela com os mesmos campos de outra já existente ("Table 788 is already defined with the same fields") apenas gera um aviso, não bloqueia — basta confirmar com Enter/Generate mesmo assim.

✅ Diagnóstico AMS

  • Chamado "não consigo salvar configuração X, tela sempre volta vazia" → antes de escalar para Basis/infra, testar navegação alternativa (seleção de linha + Enter em vez de duplo clique) em telas de Dialog Structure do SAP GUI clássico.
  • "Procedimento de precificação errado no pedido" → sempre checar as 4 chaves simultaneamente: Sales Area + Document Pricing Procedure (tipo doc) + Customer Pricing Procedure (cadastro cliente).
  • Access Sequence com Requirement (ex: Requirement 3 no PR02) é otimização de performance — evita leituras desnecessárias em tabelas de condição quando o cenário (ex: moeda estrangeira) não se aplica.

UNIT 3 — Working with Condition Records (Exercícios 10–14)

Contexto

Ferramentas de manutenção em massa de registros de condição: templates, alteração simultânea, relatórios customizados, app Fiori, e renomeação de descrições.

Sequência executada

Ex.10 (VK34 — Create with Template): reajuste futuro (01.01.2027) para P620-188 (280) e P620-288 (310)
      → sistema fecha automaticamente a validade do registro antigo em 31.12.2026
Ex.11 (VK32 — Change em massa): +5% nos dois registros → 294,00 e 325,50 EUR
      → Change Documents (VK33 → Environment → Changes) confirmam rastro de auditoria completo
Ex.12 (V/LD — Pricing Report): relatório padrão (16) + relatório customizado próprio (N9)
      criado via SPRO → Maintain Pricing Report, baseado na tabela 305
Ex.13 (Manage Prices - Sales, Fiori): editar escala (100 PC: 230→220) + copiar registro
      para novo cliente (C620-B88) sem recriar do zero
Ex.14 (Manage Prices - Sales, export/import Excel): renomear descrição do K007
      de "Customer Discount" para "VIP-Discount" — propaga até o pedido de vendas

🔧 Pegadinhas

  • VK34 fecha automaticamente a validade do registro vigente (Valid To = véspera do novo período) — evita sobreposição de dois PR00 válidos simultaneamente.
  • Descrição de tipo de condição (K007 → "VIP-Discount") é editável via export/import Excel no app Fiori, sem criar novo Condition Type — muda só o rótulo, a lógica de cálculo permanece intacta.
  • Relatório customizado (V/LD, criação via SPRO → Maintain Pricing Report) permite montar layouts próprios sem depender de ABAP — campos como Page Header vs. Item Level, exibição de escala e validade são configuráveis.

✅ Diagnóstico AMS

  • "Quem mudou esse preço e quando?" → Change Documents (VK33 → Environment → Changes) mostra usuário, data, transação, OldVal/NewVal.
  • "Preciso ver todos os preços do cliente X organizados assim" → relatório customizado (Maintain Pricing Report) em vez de exportar dado bruto e formatar manualmente.
  • "O vendedor não entende o nome K007, dá pra deixar mais claro?" → renomear descrição via app Fiori, sem tocar em customizing.

UNIT 4 — Identifying Special Functions (Exercícios 15–17)

Contexto

Condições especiais de peso/escala combinadas (Group Condition), exclusão entre grupos de condições, e rastreamento de valores cumulativos (limites de desconto).

Sequência executada

Ex.15: Criar ZW88 (frete alternativo, escala 0-30kg + corte em 0 EUR acima de 30kg)
       Posicionar step 814 no Z88PRC (antes do ZF88, step 815)
       Marcar ZF88 também como Group Condition
       Pedido com peso combinado: ZW88 e ZF88 ativos simultaneamente (peso na faixa de transição)
Ex.16: Condition Exclusion Groups Z188 (ZW88) / Z288 (ZF88), comparação tipo D
       Peso ≤30kg → ZW88 vence (verde), ZF88 suprimido (triângulo amarelo, calculado mas não efetivo)
       Peso >30kg → ZW88 zera pela escala (verde mas 0 EUR), ZF88 assume (verde, efetivo)
Ex.17: K005 com Condition Update ativado (Customizing) + Max.number.of.orders=1
       1º pedido: desconto concedido. 2º pedido: sem desconto (limite consumido)
       Alterado para Max.cond.base value=15 peças (compartilhado entre pedidos)
       Registro marcado para Deletion Indicator ao final

🔧 Pegadinhas

  • Group Condition baseada em peso aparece no cabeçalho do pedido (Goto → Header → Conditions), não isolada no item individual — comportamento fácil de confundir com "condição sumiu".
  • Triângulo amarelo (🔺) = condição calculada mas suprimida por regra de exclusão; diferente de condição simplesmente ausente (sem registro) — causas raiz completamente diferentes para investigar.
  • Recriar um registro de condição com Condition Update ativo (em vez de só editá-lo) reseta o histórico cumulativo — um limite "Max.number.of.orders" ou "Max.cond.base value" perde a memória do que já foi consumido. Confirmado na prática: um registro K005 recriado por engano tratou 15 peças "do zero" mesmo já tendo um pedido anterior consumido 10 peças do mesmo limite.
  • Alternativa a Condition Exclusion Groups: ajustar as próprias escalas dos registros para que cada condição "zere" fora da sua faixa — mais simples quando a regra é só liga/desliga por faixa, sem precisar comparar valores entre grupos.

✅ Diagnóstico AMS

  • "Desconto do contrato parou de aplicar" → checklist: contrato/registro esgotado (Max consumido)? Vencido? Pedido criado sem referência? Condição existe como registro mestre?
  • "Apliquei um novo limite mas ele contabilizou peças que já tinham sido vendidas antes" → causa raiz típica: registro de condição foi recriado em vez de editado, perdendo o rastro cumulativo (KONV acumulado).
  • "Por que não vejo o frete X na nota" → distinguir ausência (sem registro) de supressão por exclusão (triângulo amarelo).

UNIT 5 — Identifying Condition Types (Exercícios 18–19)

Contexto

Tipos de condição especiais para negociação (HM00, PN00, PMIN) e precificação por hierarquia de clientes (HI02).

Sequência executada

Ex.18: HM00 no cabeçalho (400 EUR) → rateado proporcionalmente entre 2 itens (114,94 + 285,06)
       PN00 manual no item (200 EUR) → suprime PR00 e K007 (ficam amarelos, visíveis mas inativos)
       PMIN criado (300 EUR) → piso de preço, trava contra desconto excessivo
Ex.19: VDH1N — vincular C620-A88 sob nó C620-ZEW (TOPCO Western Europe)
       HI02 criado no nó C620-ZE (TOPCO Europe, um nível acima), material P620-288, 50 EUR
       Pedido do cliente C620-A88 herda o desconto do nó pai automaticamente

🔧 Pegadinhas

  • HM00 é Group Condition (rateio proporcional, como HB00); PN00 é diferente — substitui/suprime as condições de preço-base do item (não rateia, "zera" o que existia).
  • Dois erros de "campo trocado" no VDH1N identificados nesta prática:
  • Ao buscar o registro HI02, o campo Customer da tela de seleção veio pré-preenchido com o nó raiz (C620-ZZ) em vez do nó correto (C620-ZE) — resultado: registro criado na chave errada, sem aparecer no pedido.
  • Ao vincular o cliente na hierarquia, o número C620-A88 foi digitado no campo "Higher-level customer" (que deveria ser o nó pai, C620-ZEW) em vez do campo "Customer" (mais abaixo, onde entra o cliente a vincular) — inverteu a lógica da vinculação.
  • Esses dois erros, isolados, geram exatamente o mesmo sintoma ("desconto não aparece") — é preciso verificar cada objeto separadamente (primeiro o registro HI02 via VK13, depois a hierarquia via VDH1N) antes de testar o pedido novamente.

✅ Diagnóstico AMS

  • "Negociei um valor fechado com o cliente, preciso que ignore os descontos automáticos" → PN00 (preço líquido manual por item).
  • "Cliente ficou abaixo do preço mínimo permitido" → verificar se existe registro PMIN cadastrado para o material.
  • "Acordo comercial da matriz não está chegando nas filiais" → verificar em duas camadas: (1) registro de condição de hierarquia na chave certa (nó pai correto), (2) vinculação do cliente-filho ao nó certo na árvore (VDH1N) — nunca assumir que "parece certo" sem checar campo a campo.

UNIT 6 — Getting to Know Condition Contract Management (Exercícios 20–26)

Contexto

Mundo separado de Rebates/Bonificações (Condition Contract Management), com trilha de determinação de precificação própria (Document Schema Group), distinta da precificação de pedidos de venda comuns.

Sequência executada

Ex.20: Document Schema Group do tipo 0S12 (Sales Rebate Credit) = 0S (Sales Rebate)
       Determinação: 0S → Pricing Procedure A10005 (Rebate Germany)
Ex.21: 2 ciclos completos O2C para C620-B88 (10 PC de P620-388 cada)
       Pedidos 445/446 → Entregas 80000183/184 (GI) → Faturas 90000137/138
       [nota: entrega precisa de Selection Date >= data confirmada no Schedule Lines,
        senão "No schedule lines due for delivery up to the selected date"]
Ex.22: WCOCO — Condition Contract 2000000001 (tipo 0S01, cliente C620-B88, 01.01-31.12)
       Business Volume Selection: Customer C620-B88 + Material P620-388
       Condições RES1 (10 EUR, rebate) + REA1 (-10 EUR, accrual)
       Settlement Calendar: AJ (Annual arrangement) → gerado automaticamente 31.12
Ex.23: Delta Accruals run (WB2R_SC, Live Run) → 200 EUR de provisão (10×20 PC)
Ex.24 (opcional): Business Volume report (WB2R_BUSVOL): 20 PC / REBV 6.200
       Partial Settlement → Credit Memo 0000000002 = 200 EUR net (Detailed Statement
       confirma as 2 faturas SD como base)
Ex.25 (opcional): 3º pedido (448, 10+5 PC) → Entrega 80000187 → Fatura 90000139
Ex.26 (opcional): Final Settlement (whole year) → Credit Memo 0000000003 = 100 EUR net
       (30 PC totais - 20 PC já liquidados na parcial = 10 PC restantes × 10 EUR)
       Monitor Customer Condition Contracts + Monitor Settlement Documents (Fiori) confirmam

🔧 Pegadinhas

  • Condition Contract Management usa uma trilha de determinação completamente separada dos pedidos de venda: Document Schema Group (não Document/Customer Pricing Procedure) → Pricing Procedure de settlement (A10005 etc.).
  • Entrega com "No schedule lines due" → verificar a Confirmed Delivery Date real no Schedule Lines do pedido (VA03) antes de escolher a Selection Date da entrega — o prazo de entrega calculado pode ultrapassar o "+10 dias" padrão.
  • Final Settlement não recalcula do zero — ele rastreia o que já foi liquidado em runs anteriores (delta accrual, partial settlement) e só fecha a diferença pendente, evitando pagamento duplicado de rebate.

✅ Diagnóstico AMS

  • Chamado "o rebate está calculando errado" → investigação NÃO começa no pricing procedure de vendas comum; começa no Document Schema Group do tipo de settlement document.
  • "Cliente reclama que a entrega não foi criada" → antes de qualquer coisa, checar a Confirmed Delivery Date no pedido — Selection Date da entrega tem que ser igual ou posterior.
  • Fechamento contábil/rebate: Delta Accruals (provisão antecipada) → Partial Settlement (crédito parcial) → Final Settlement (fecha a diferença) é o ciclo de vida completo de um acordo de rebate.

UNIT 8 — Appendix: Pricing Agreements (Exercício 27, opcional)

Contexto

Rastreabilidade de campanhas promocionais (Promotion + Sales Deal) até o documento fiscal final, para fins de relatório gerencial.

Sequência executada

VB31: Promotion 1 (tipo 0030, "Group88", Terms of payment ZB03)
VB21: Sales Deal 2, criado COM REFERÊNCIA à Promotion 1 (herda ZB03 automaticamente)
VB22: KA00 (10% desconto) cadastrado dentro do Sales Deal, chave Customer C620-B88 + Material P620-288
Pedido 449 (P620-288, 10 PC) → KA00 aplicado automaticamente (-310,00 EUR, -10%)
       sem precisar referenciar manualmente o Sales Deal
Entrega 80000188 → Fatura 90000140
VF03 → Item Details → bloco "Price Data": Promotion 1 e Sales Deal 2 preservados até a fatura

🔧 Pegadinhas

  • O desconto KA00 é aplicado pela sequência de acesso normal de precificação (chave Customer+Material) — não depende do pedido "saber" que existe uma Promotion/Sales Deal por trás. O vínculo Sales Deal → Promotion serve só para rastreabilidade de relatório.
  • Os campos Sales Promotion / Sales Deal na fatura ficam na aba "Item Details", bloco "Price Data" — não em Sales A nem Sales B (diferente de outros campos administrativos vistos em exercícios anteriores).

✅ Diagnóstico AMS

  • "Não conseguimos saber quais faturas vieram de qual campanha" → verificar se o pedido foi criado com referência ao Sales Deal (mesmo que o desconto já viesse automático pela precificação padrão) — só a referência propaga o número até a fatura.
